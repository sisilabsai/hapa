// The Foundational Decision
PWA vs NATIVE

Before any other technology decision, this one. Everything downstream depends on it. The choice is not about preference — it is about what Hapa's core product requires to function correctly for its primary users.

Evaluation Matrix
Requirement Why It Matters for Hapa PWA Flutter Native
Background Location City-switch detection, predictive notifications, "moved to Nairobi" trigger ✗ BROKEN on iOS. Limited on Android. ✓ Full native API access
Push Notifications (iOS) Hapa Flash alerts, predictive recommendations, proximity Boosts ✗ Requires manual home screen install. Most users never do. ✓ Full APNs + FCM support
Low-end Android Performance Tecno, Infinix, Samsung A-series — primary African market devices ✗ Browser engine overhead. Scroll jank on 2GB RAM. ✓ Compiles to native ARM. Indistinguishable from native.
Offline-First 2G/3G drops. Feed must load. Posts must queue. Maps must render. ~ Service workers fragile. Browser clears cache under memory pressure. ✓ SQLite local DB. Full offline control.

Mobile Money SDK Flutterwave + M-Pesa + MTN MoMo native integrations ~ Web redirects. Poor UX. Higher drop-off. ✓ Native SDK integration. In-app payment sheets.
Development Speed One codebase for iOS and Android ✓ Fast to prototype ✓ Single codebase. Fast with right team.
App Store Distribution Discovery, credibility, enterprise partnerships ✗ Not on App Store / Play Store natively ✓ Full App Store + Play Store presence

Final Decision — Flutter Native for Mobile. Next.js for Business Dashboard.

PWA fails on the three most critical Hapa requirements: background location, iOS push notifications, and low-end Android performance. These are not edge cases — they are the core product. A PWA Hapa is a fundamentally broken Hapa. Flutter delivers native ARM performance on every device, full API access, one codebase, and offline-first capability. The business owner dashboard — analytics, bookings, Boost management — lives on the web as a Next.js application. This is natural: business owners manage their listings on desktop. Users experience Hapa on their phones.

FRONTEND STACK

Two surfaces. One for users and creators on mobile. One for business owners on web. Different tools, same design system, shared component logic where possible.

1.1 — Mobile App: Flutter
Flutter 3.x
Core Framework
Cross-platform mobile framework compiling to native ARM code for both iOS and Android. Single codebase. No JavaScript bridge. Full native API access.
Native performance on Tecno/Infinix devices. Low-end Android feels the difference.
Dart
Language
Flutter's compiled language. Strongly typed, null-safe, fast to learn. Ahead-of-time compilation produces small, efficient binaries that load fast even on slow storage.
AOT compilation = fast startup. Critical for first impression on low-end devices.
Riverpod
State Management
Compile-safe state management for Flutter. Handles the complex state of a location-aware, real-time social platform cleanly. Replaces Provider pattern with better testability.
Location state + feed state + auth state + social state — all managed without spaghetti.
SQLite / Drift
Local Database
Drift (formerly Moor) provides a type-safe SQLite wrapper for Flutter. Stores feed posts, cached business listings, saved places, draft posts, and queued uploads locally.
Offline-first is non-negotiable. Feed loads with no internet. Posts queue when connection drops.
Mapbox Flutter SDK
Maps & Location
Native Mapbox SDK for Flutter. Renders custom Hapa-styled maps, handles offline tile caching, business pin clustering, and route display with true native performance.
Offline map tiles. Custom Hapa visual identity on maps. Works on 2G — Google Maps does not.
Geolocator + Background Location
Location Services
Geolocator for foreground GPS. background_location package for city-switch detection when app is backgrounded. Platform-specific permissions handled gracefully with user-friendly explanations.
City-switch detection is the magic moment. Requires background location done right.
1.2 — Key Flutter Architecture Principles
Offline-First Strategy
  • All feed reads hit SQLite cache first — network is a refresh, not a requirement
  • Post creation queues locally with UUID — uploads when connection returns
  • Business listings cached per city with 24-hour TTL
  • Mapbox tiles pre-cached for current city on wifi connection
  • Cultural Guide content for current city fully available offline
  • Connectivity package monitors connection state — UI adapts gracefully
Performance Targets
  • Cold start to feed: under 2.5 seconds on Tecno Spark (2GB RAM, Android 11)
  • Feed scroll: 60fps maintained. Zero jank tolerance.
  • Image load: WebP format, progressive loading, thumbnail-first
  • Map render: offline tiles load in under 1 second in current city
  • Location detection: city-level accuracy within 3 seconds of app open
  • Push notification delivery: under 500ms from server trigger to device display
1.3 — Business Web Dashboard: Next.js
Next.js 15
Web Framework
React-based framework with App Router, server-side rendering, and built-in API routes. Powers the Hapa Business dashboard — analytics, Boost management, bookings, creator partnerships.
Business owners manage on desktop. SSR gives fast initial load. App Router handles complex dashboard routing cleanly.
TypeScript
Language
Strongly typed JavaScript across the entire web codebase. Shared type definitions with the backend API contract. Catches integration bugs at compile time not runtime.
Shared API types between Next.js dashboard and Go backend prevents silent contract breaks.
Recharts + Mapbox GL JS
Data Visualisation
Recharts for business analytics charts — views, bookings, Boost performance. Mapbox GL JS for the business dashboard map showing their pin location, nearby user activity radius, and Boost reach.
Business owners need to see their reach visually. Numbers alone don't sell the value of upgrading.

BACKEND ARCHITECTURE

Go as the primary backend language. A modular monolith architecture with clear domain boundaries — designed for eventual microservice extraction without the distributed systems complexity that kills early-stage teams.

"// Don't build fifteen microservices on day one. Build a monolith that
// respects domain boundaries and can be split when traffic demands it."

// Architecture Principle
2.1 — Why Go
Concurrency
Goroutines + Channels
Go's goroutine model handles thousands of concurrent location queries, feed requests, and WebSocket connections with minimal memory overhead. Each goroutine costs ~2KB vs ~1MB for an OS thread.
Hapa's peak load: thousands of users all querying "what's near me right now" simultaneously.
Performance
Compiled Binary
Go compiles to a single static binary with no runtime dependencies. Cold starts in milliseconds on Cloud Run. CPU-efficient under geospatial query load that would bring a Node.js server to its knees.
PostGIS geospatial queries are CPU-intensive. Go handles the computation layer efficiently.
Simplicity
Explicit Over Magic
Go has no hidden magic, no decorators, no complex ORM behaviour to debug. What you read is what runs. This dramatically reduces debugging time in a complex location-aware platform.
A small team maintaining a complex platform needs code that explains itself.

// Data Layer
DATABASE ARCHITECTURE

PostgreSQL with PostGIS is the foundation. Every other data store exists because PostgreSQL is the wrong tool for that specific job. No database is added without a clear, justified reason.

3.1 — Primary Store: PostgreSQL + PostGIS
PostgreSQL 16
Primary Database
ACID-compliant relational database for all structured data. Users, businesses, posts, reviews, bookings, creator partnerships, payments, moderation logs. The single source of truth.
ACID transactions for bookings and payments. Proven reliability. Best ecosystem for PostGIS.
PostGIS Extension
Geospatial Engine
Adds geographic object support to PostgreSQL. Enables: "find all businesses within 500m of this coordinate", distance-sorted feed queries, polygon-based neighbourhood filtering, and radius-based Boost targeting.
Hapa's entire recommendation and discovery model runs on geospatial queries. PostGIS is the engine.
Redis 7
Cache + Feed Store
Pre-computed feed buckets per location grid cell. User session tokens. Like/Been Here counts. Flash post real-time state. Rate limiting counters. Leaderboard data for local reputation scores.
Feed requests hit Redis in microseconds. PostgreSQL for feed queries at scale would be too slow.
3.2 — Core Schema Design

3.3 — Supporting Data Stores
Meilisearch — Search Engine
  • Powers all user-facing search: "suya near me", "mechanic Surulere", "hotel under 50k"
  • Typo-tolerant — "resturant" finds "restaurant". Critical for multilingual users.
  • Instant search — results appear as user types. No submit button.
  • Faceted filtering by category, price range, rating, distance
  • Synced from PostgreSQL via event-driven pipeline — search index always fresh
  • Handles Swahili, Yoruba, Luganda tokenisation better than Elasticsearch out-of-box
Redis Data Structures in Use
  • Sorted Sets — feed ranking per location grid cell (GeoHash bucketing)
  • Hashes — user session data, JWT refresh tokens
  • Counters — been_here counts, flash pulse counts, like counts (synced to PG hourly)
  • Lists — notification queues per user
  • Sets — user follower/following IDs (fast intersection for feed filtering)
  • Pub/Sub — real-time event distribution to WebSocket connections
3.4 — Key PostGIS Queries
-- Find all businesses within 1km of user, sorted by distance + rating SELECT b.*, ST_Distance(b.location, ST_Point(32.5825, 0.3476)::geography) AS distance_m FROM businesses b WHERE ST_DWithin( b.location, ST_Point(32.5825, 0.3476)::geography, 1000 -- 1000 metres ) AND b.category = 'food_dining' ORDER BY (distance_m * 0.4) + ((5 - b.rating_avg) * 200) -- distance + rating blend LIMIT 20; -- Detect if user has moved cities (for context switch trigger) SELECT city, COUNT(*) AS pings FROM user_locations WHERE user_id = $1 AND recorded_at > NOW() - INTERVAL '30 minutes' GROUP BY city ORDER BY pings DESC LIMIT 1; -- If result.city != user.current_city → trigger context switch

// Geospatial Layer
LOCATION INFRASTRUCTURE

Location is Hapa's core product. The geospatial stack must be fast, battery-efficient, accurate enough to serve recommendations but not so precise it becomes surveillance. Every design choice reflects that balance.

Mapbox
Maps & Tiles
Custom Hapa map style. Offline tile caching for current city. Business pin clustering at zoom levels. Route display for navigation. Significantly faster than Google Maps on low-end Android.
Offline tiles work on 2G. Custom visual identity. 40% cheaper than Google Maps at scale.
OpenStreetMap + Pelias
Geocoding
Self-hosted Pelias geocoder using OpenStreetMap data. Converts GPS coordinates to city/neighbourhood names. OSM has dramatically better coverage of African informal settlement names than Google.
Google Geocoding returns "Unnamed Road" in Kibera. OSM returns "Kibera, Nairobi" with neighbourhood detail.
GeoHash Bucketing
Feed Partitioning
The city is divided into GeoHash grid cells (~1.2km × 0.6km). Feed content is pre-computed per cell and cached in Redis. Users in the same cell share a feed cache — dramatically reducing database load at scale.
Without bucketing, every user location query hits PostgreSQL independently. With it, one cache serves thousands of users in the same area.
4.1 — Location Signal Processing
GPS Smoothing Pipeline
  • Raw GPS signals are noisy — a stationary user shows slightly different coordinates every few seconds. A Kalman filter smooths this before any data touches the database.
  • City-level accuracy is all Hapa needs for feed filtering. Neighbourhood-level for Boost targeting. Precise coordinates only for business pin proximity checks.
  • Location updates sent to server maximum every 90 seconds while app is open — not continuously. Protects user battery and mobile data budget.
  • Background location pings every 15 minutes at city-level granularity only — enough to detect a city switch, not enough to track movement within a city.
  • Location data older than 90 days is automatically purged from user_locations table via scheduled PostgreSQL job.
4.2 — City Switch Detection Flow
// City switch detection — runs on background location ping func CheckCitySwitch(userID string, newLat, newLng float64) { currentCity := cache.GetUserCity(userID) detectedCity := geocoder.CityFromCoords(newLat, newLng) if detectedCity != currentCity { // Confirm with 3 consecutive pings before triggering count := cache.IncrCityPingCount(userID, detectedCity) if count >= 3 { db.UpdateUserCity(userID, detectedCity) cache.InvalidateUserFeed(userID) notifications.Send(userID, CitySwitchNotification(detectedCity)) events.Publish("user.city_switched", userID, detectedCity) } } } // 3-ping confirmation prevents false triggers during transit through a city

// Intelligence Layer
AI & ML STACK

Three distinct AI concerns. The conversational layer that answers natural language queries. The recommendation engine that anticipates behaviour. The moderation layer that protects the community. Each has different requirements and different tools.

Claude API
Conversational AI
Powers Hapa's natural language query layer. "Find me a hotel near me under 50,000 UGX with a generator." Claude interprets the query, retrieves structured data from PostgreSQL, ranks results, and returns a conversational response with booking links.
Multilingual. Handles African context nuance. Understands currencies, local references, and conversational phrasing that rigid search cannot.
Python + scikit-learn
Recommendation Engine
Behavioural recommendation pipeline. Collaborative filtering on user-location-content interaction matrix. Time-of-day models. Interest-to-business affinity scoring. Runs as a separate Python service, results stored in Redis for fast retrieval.
Python has the richest ML ecosystem. Separate service means it can be scaled or replaced independently of the Go backend.
Google Vision + BERT
Content Moderation AI
Google Cloud Vision API for image moderation — inappropriate content detected before publish. Fine-tuned multilingual BERT model for text moderation in English, Swahili, Yoruba, and Luganda. Runs async — content publishes optimistically and is removed if flagged.
Synchronous moderation kills posting UX. Async moderation with instant optimistic publish feels fast. Most content is fine. Bad content is caught within seconds.

5.2 — Recommendation Engine Pipeline
Input Signals (per user)
  • Posts interacted with — type, location, time of day, day of week
  • Businesses visited (proximity inferred from location history)
  • Search queries — keywords and categories
  • Been Here confirmations — highest-quality positive signal
  • Creator follows — their content preferences by proxy
  • Community circles joined — explicit interest declaration
  • Notification opens vs dismissals — content relevance feedback
  • Time-of-day activity patterns — when are they most active
Output — Ranked Recommendation Sets
  • Feed ranking weights — personalised per user, refreshed every 6 hours
  • Predictive notification content — what to send and when
  • People discovery ranking — who to surface in Hapa People
  • Business discovery boost — which businesses to surface above standard placement
  • Creator discovery — which local creators match this user's profile
  • Challenge relevance — which city challenges this user is likely to participate in
  • Cross-city preload — if user regularly travels, pre-cache recommendations for likely destinations

// Cloud & DevOps
INFRASTRUCTURE & DEVOPS

GCP Johannesburg region as primary. Cloudflare for CDN and media. Cloud Run for early-stage auto-scaling. GKE when traffic justifies the operational complexity. CI/CD from day one.

GCP — Johannesburg
Primary Cloud Region
Google Cloud Platform's Africa South 1 region (Johannesburg). Lowest latency to East and West African users of any major cloud provider. PostgreSQL on Cloud SQL, Go services on Cloud Run, ML pipeline on Vertex AI.
Latency from Johannesburg to Kampala: ~40ms. From Europe: ~200ms. That difference is felt in every API call.
Cloud Run → GKE
Container Orchestration
Cloud Run for v1 — serverless containers that scale to zero at night and handle traffic spikes automatically. Migrate to GKE (Kubernetes) when stateful services and inter-service communication requires it. No Kubernetes complexity until it's earned.
Cloud Run at low traffic costs near-zero. Handles African peak hours (evenings/weekends) automatically without pre-provisioning.
Cloudflare R2 + CDN
Media & CDN
All user media (photos, videos, profile images) stored in Cloudflare R2. Served via Cloudflare's CDN — one of the strongest network presences in Africa. Images auto-compressed to WebP. Videos transcoded to adaptive bitrate for 2G compatibility.
A photo post in Lagos reaching a user in Kampala should load in under 1 second. Only possible with African CDN PoPs.
Ably
Real-time WebSockets
Managed WebSocket infrastructure for real-time features: Flash post alerts, live "users here" counts, instant booking confirmations, notification delivery. Ably has African edge servers reducing WebSocket latency.
Building and scaling a custom WebSocket server is expensive engineering time. Ably handles it and is cheaper than the engineering cost of alternatives.
GitHub Actions
CI/CD Pipeline
Automated testing, linting, and deployment on every push. Go backend: unit tests + integration tests against test PostgreSQL instance. Flutter: widget tests + integration tests on emulator. Deployment to Cloud Run on merge to main.
Shipping broken code to African users who paid data to download an update is unacceptable. CI catches regressions before they ship.
Sentry + Grafana
Monitoring & Observability
Sentry for error tracking in both Flutter app and Go backend — with African user context (device model, OS version, network type) attached to every error. Grafana dashboards for API latency, database query performance, and location service accuracy metrics.
A crash on a Tecno device running Android 10 must surface differently from a crash on iPhone 15. Device context is critical for African market debugging.
6.1 — Media Processing Pipeline
Image & Video Pipeline
  • User uploads image → Flutter compresses client-side to max 800KB before upload — saves mobile data
  • Server receives → Cloud Run worker converts to WebP format (30–50% smaller than JPEG at same quality)
  • Three sizes generated: thumbnail (150px), feed (600px), full (1200px) — served based on network speed
  • Video uploads → transcoded to HLS adaptive bitrate: 360p for 2G, 720p for 3G+, 1080p for WiFi
  • All media served through Cloudflare CDN with aggressive caching headers (1 year TTL)
  • Content-addressed storage — identical images stored once, served via hash-based URLs

// Financial Layer
PAYMENTS & MOBILE MONEY

Stripe is not the answer for Africa. Mobile money is. Every payment decision is made around the reality that M-Pesa, MTN MoMo, and Airtel Money are how the majority of Hapa's users and business owners transact.

Flutterwave
Primary Payment Aggregator
Handles M-Pesa (Kenya), MTN MoMo (Uganda/Ghana/Rwanda), Airtel Money (Uganda/Tanzania/Zambia), Zamtel, Orange Money, and card payments across 34 African countries through a single API. Primary choice for pan-African coverage.
Single integration covers all East and West African mobile money. Critical for Hapa Boost payments and creator payouts.
Paystack
Secondary / Nigeria-First
Strongest presence in Nigeria with the cleanest API. Used as primary processor for Nigerian market (Lagos, Abuja, Port Harcourt) where Paystack has deepest bank and mobile money integration. Secondary fallback for other markets.
Nigeria is Hapa's largest single-country market. Paystack's Nigeria coverage is unmatched. Dual integration reduces single-point-of-failure risk.
7.1 — Payment Flows
User Payments (Inbound)
  • Hapa Pro subscription — mobile money monthly recurring or card
  • In-app hotel/restaurant booking — mobile money preferred, card fallback
  • Creator subscription — fan pays creator monthly fee via mobile money
  • Tipping creators — one-tap mobile money tip from content
  • All payments confirmed via webhook before service activates
Business Payments (Inbound)
  • Monthly listing fees — auto-debit from registered mobile money account
  • Hapa Boost purchases — pay-per-push, mobile money or card
  • Booking commissions — deducted from booking payment before remittance
  • Creator partnership fees — brokered through platform, deducted at source
  • Invoices sent via WhatsApp for businesses on monthly billing
Creator & Business Payouts (Outbound)
  • Creator Fund distributions — weekly, mobile money or bank transfer
  • Business booking remittances — net of commission, weekly settlement
  • Partnership deal payments — released on completion confirmation
  • Minimum payout threshold: 10,000 UGX / 500 KES / 500 NGN
  • Payout via Flutterwave Transfers API — same rails as collection

// Security Layer
SECURITY ARCHITECTURE

Location data is the most sensitive data Hapa holds. Security is not a feature — it is the foundation. A breach of location data is not just a technical failure. It is a betrayal of user trust that cannot be recovered from.

Authentication

  • Phone number + OTP as primary auth. No passwords stored.
  • JWT access tokens (15-minute expiry) + refresh tokens (30-day expiry) stored in secure storage on device
  • Refresh token rotation — every use issues a new refresh token. Old one invalidated.
  • Device fingerprinting — new device login triggers OTP re-verification
  • Rate limiting on OTP requests — max 3 per phone per hour, exponential backoff
  • Google OAuth as secondary path — token verified server-side, never trusted client-side

Location Data Protection

  • Precise coordinates never exposed to other users via API — city and neighbourhood only
  • Location history stored encrypted at rest in PostgreSQL (pgcrypto extension)
  • Location data purged after 90 days via automated pg_cron job
  • Background location requires explicit separate permission — not bundled with foreground
  • GPS smoothing applied before storage — no raw coordinate sequences stored
  • Data access logs for all location table queries — auditable trail

API Security

  • All endpoints require valid JWT — no unauthenticated data access
  • Rate limiting per user per endpoint — prevents abuse and scraping
  • Request signing for sensitive operations (bookings, payments)
  • Input validation and parameterised queries everywhere — SQL injection impossible
  • HTTPS only — no HTTP fallback. HSTS enforced.
  • API versioning — breaking changes never affect live clients silently

Payment Security

  • Hapa never stores card numbers — Flutterwave/Paystack tokenise at point of entry
  • Mobile money transactions verified via webhook signature (HMAC-SHA256)
  • Payment amounts verified server-side before any service activation — never trust client
  • Idempotency keys on all payment requests — duplicate charges impossible
  • Suspicious payment patterns flagged for manual review
  • PCI DSS compliance delegated entirely to Flutterwave and Paystack
